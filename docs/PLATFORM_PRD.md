# PRD · rs-face 人脸识别平台

> 目标：把 rs-face 做成一个**自托管、可生产使用的人脸识别平台**，而不只是一组算法 demo。
> 本文档是唯一的目标与验收基准。维护者（Claude）按里程碑持续迭代；每个阶段必须通过"验收标准"（真实数据/真实凭据，不接受只编译或口头确认）。

---

## 1. 产品定位

一个可在 Jetson（GPU）上 `docker compose up` 即运行的人脸识别平台，提供：人脸检测 → 质量校验 → **活体检测（防伪）** → 特征提取 → 人脸库（gallery）管理 → 1:1 比对 / 1:N 识别 → 视频流实时识别 → Web 控制台 / OpenAPI。所有关键指标有真实实测数据，结果可持久化、可备份恢复。

非目标：不追求刷榜 SOTA；不做多租户 SaaS；不做支付/账号体系（单机平台 + 简单访问控制）。

---

## 2. 平台能力清单（Definition of Done）

| 模块 | 能力要求 |
|---|---|
| 检测 | 图像/视频/RTSP 流多源输入；多尺度人脸检测，输出框 + 关键点 |
| 质量 | 模糊/遮挡/过小/姿态/光照过滤，拒绝低质量样本入库 |
| 活体 | MiniFASNet 静默活体，真人/翻拍/屏幕攻击可区分，输出 spoof 标签 + 置信度 |
| 特征 | GPU 加速 embedding，模型可替换；特征可持久化 |
| 人脸库 | 人员 CRUD、一人多脸、增删改查、去重、导出 |
| 1:1 比对 | 人脸核身：相似度 + 阈值 + 活体门控 |
| 1:N 识别 | top-k 识别结果 + 置信度；批量/实时 |
| 视频流 | 实时检测+识别+活体叠加，RTSP 拉流 / SSE 推流 |
| Web 控制台 | 人员管理、实时预览、任务/系统状态、可演示 |
| OpenAPI | REST 文档化，鉴权，错误码规范 |
| 运维 | 健康检查、日志、指标、备份恢复、GPU/CPU 双部署 |

## 3. 里程碑与阶段性验收

每阶段验收必须给出**真实实测证据**（命令 + 输出 / 数据文件路径）。指标阈值为最低准入，达不到不进入下一阶段。

### M1 · 核心链路可用（检测→特征→识别）
- `cargo test` 全绿；`docker compose up -d` 三服务健康
- 真实样本集（≥200 张 / ≥50 人）上：检测召回率 ≥ 98%；1:N top-1 ≥ 95%，top-5 ≥ 99%（标准人脸）
- gallery 持久化 + 容器重建后数据仍在；备份恢复脚本实测通过
- 交付物：识别评测报告 CSV/MD（含混淆分布）、API 示例

### M2 · 活体防伪上线
- 独立真人 vs 攻击测试集（各 ≥100 条）
- 验收：**FAR ≤ 1%（攻击被放行率）**，**FRR ≤ 5%（真人被拒率）**，给出阈值与 ROC
- 活体门控接入 1:1/1:N/注册接口，可配置开/关与阈值
- GPU 容器内真人/翻拍/屏幕实测视频或日志证据

### M3 · 视频流实时识别
- 720p RTSP 实时流水线：**≥ 15 FPS**（Jetson GPU），检测+活体+识别延迟 ≤ 300ms
- 连续运行 ≥ 30 分钟无崩溃、无内存泄漏（前后 RSS 对比）
- SSE/WebRTC 可视预览叠加框与身份

### M4 · 平台化（Web + API + 运维）
- Web 控制台：人脸库管理 + 实时预览 + 任务/系统健康，浏览器端可完整走通"录入→识别"
- OpenAPI（Swagger）+ Token 鉴权 + 统一错误码
- 健康检查、Prometheus 指标、结构化日志、一键备份/恢复文档
- 冷启动部署文档：从空机器 `docker compose up` 到可用 ≤ 30 分钟

---

## 4. 工程硬约束（不可违反）

- 平台服务只走 `docker compose`；禁止 host 裸跑 server
- 算法开发走原生 `cargo test / clippy / bench`，不套 docker
- 数据走 bind mount（`data/`），不用 named volume
- 每次改动经真实测试验证；一个可交付点一次 commit，提交信息清晰
- 性能/质量用**真实数据集**度量，禁止编造指标
- 新增文件位置遵守 `STRUCTURE.md`

## 5. 当前状态（2026-09-21）

- 已完成：S3/存储修复、telemetry、队列治理、GPU 部署；MiniFASNet 活体模块初版（提交 25dbbc9）
- 平台审计已完成（`docs/audit-platform.md`，证据已核对）。关键结论：
  - jobs 的 464 error 中 **462 条 = server 重启的 orphaned 回收（运维噪声，非 bug）**；真 bug 仅 2 条
  - **P0 闭环缺口（最高优先，先于 M2/M3）：**
    1. **persons 人脸库完全缺失**（无表/CRUD/前端，录入→识别闭环不存在）
    2. **API 零鉴权**
    3. **活体未接入平台**（容器无 ONNX、worker 不调用）
    4. **流任务 ffmpeg 失败永久挂起**（僵尸 + 无错误码）
- 修订后的推进顺序：**先补 persons 人脸库闭环（M1 的平台化部分）→ API 鉴权 → 活体接入与 M2 验证 → 修流任务挂起 → M3 视频流 → M4**
- M2 活体 FAR/FRR 评测已完成（`docs/eval-m2.md`，数据 data/eval_m2/，证据已独立复算）：
  区分度高（**AUC=0.988 / EER≈5.6%**，719 帧），但**未达 M2 联合验收**：
  FAR≤1% 时 FRR≈19%；FRR 地板≈12.3%（22/179 真人连 argmax 都误判，主因 256px JPEG 重编码域 ≠ 训练域）。
  **结论：活体暂不作为生产硬门控上线**，需先做域内采集复测 / 微调 / 校准（见 eval-m2.md 后续建议）。
- M1 指标评测仍由独立评测脚本产出（docs/eval-m1.md），不与主开发并发改代码
